# 기존 할부와 카드대금 연결

## 사용 흐름

1. 카드 상세의 **기존 할부 등록**에서 첫 결제일, 잔여 개월, 잔여 총액, 메모를 입력합니다. 첫 결제일은 카드 결제일과 맞춥니다.
2. 남은 금액을 개월 수로 나누어 회차별 일정을 생성합니다. 소수 둘째 자리까지 나누고 남는 차액은 마지막 회차에 포함합니다. 31일 결제는 짧은 달의 말일로 조정합니다.
3. 예정 거래의 **카드에 연결된 반복 할부**에 표시됩니다. 달력에서는 같은 카드·결제월의 할부들을 카드 결제 예정 한 건에 합산합니다.
4. 달력에서 확정하거나 카드 상세의 **카드대금 납부**에서 결제월과 실제 출금일·총액을 입력합니다.
5. 계좌에서 실제 총액을 출금하고 해당 결제월에 연결된 각 할부를 한 회차씩 차감합니다. 마지막 회차를 납부하면 잔여 금액·개월이 0이 되고 자동 완납 처리됩니다.

예를 들어 잔여 3개월·30만 원이면 매월 10만 원씩 연결됩니다. 첫 결제월에 일반 사용액 5만 원을 포함해 15만 원을 납부하면 계좌에서는 15만 원이 줄고, 할부는 2개월·20만 원이 됩니다. 출금일이 다음 달이어도 선택한 결제월의 회차를 처리합니다.

## 처리 기준

- 기존 할부는 과거 구매의 남은 납부 일정입니다. 등록·납부로 새 지출 원장을 만들지 않아 구매 지출을 중복 집계하지 않습니다.
- 반복 지출 목록은 일반 `recurring_plan`과 카드 할부 일정을 함께 표시합니다. 할부마다 별도의 일반 지출을 만들어 이중 출금하지 않습니다.
- 실제 카드 청구액은 일반 사용액 등을 포함할 수 있습니다. 자동으로 계산한 할부 합계는 총 청구액이 아니므로 실제 총 출금액을 직접 확인합니다.
- 한 결제월의 납부는 해당 월 할부 전액이 포함된 것으로 처리합니다. 총 출금액이 할부 합계보다 적으면 거부합니다. 부분 납부·리볼빙·특정 할부만 선납하는 배분은 지원하지 않습니다.
- 같은 카드 결제월을 두 번 확정할 수 없습니다. 카드 상세와 달력 어느 경로로 처리해도 같은 예정과 납부 이력을 사용합니다.
- 납부 전에는 수정하면 미처리 회차를 다시 생성합니다. 납부 후에는 이력을 보존하기 위해 직접 수정을 막습니다. 계약 변경이 필요하면 비활성화 후 남은 조건으로 새로 등록합니다.
- 비활성화는 남은 회차를 취소하고 아직 미처리인 카드 예정의 합계를 갱신합니다. 이미 납부한 회차는 보존합니다.
- 진행 중인 할부가 연결된 카드 예정은 바로 취소할 수 없습니다. 날짜 변경 또는 할부 비활성화 후 취소를 사용합니다. 카드 해지도 할부 완납 또는 비활성화 후 가능합니다.

## 기존 DB 적용

애플리케이션을 중지하고 DB를 백업한 뒤, 사용하는 DB에 [20260912_installment_schedule.sql](../db/migrations/20260912_installment_schedule.sql)을 적용하고 새 빌드로 재시작합니다. 새 DB는 최신 `schema.sql`에 이미 포함되어 있습니다. 앱의 SQL 자동 초기화는 꺼져 있으므로 소스 변경만으로 기존 DB가 바뀌지는 않습니다.

```powershell
# DB 사용자와 DB 이름은 실제 사용하는 값으로 지정합니다.
psql -U <DB사용자> -d <DB이름> -v ON_ERROR_STOP=1 -f db/migrations/20260912_installment_schedule.sql
.\gradlew.bat clean build
.\gradlew.bat bootRun
```

기존 할부에는 첫 결제일 정보가 없었습니다. 마이그레이션은 다음 도래 카드 결제일부터 배치하되 이미 완료·취소한 결제월 이후로 잡습니다. 이미 기록된 과거 카드 출금에 소급 연결하거나 잔액을 차감하지 않습니다. 첫 결제월이 실제 청구와 다르면 첫 납부 전에 카드 상세에서 수정합니다. 이미 존재하는 회차는 재실행해도 중복 생성하지 않습니다.

## 구현 위치

| 영역 | 파일/데이터 |
|---|---|
| 회차 계산·생성·납부 반영 | `InstallmentService`, `InstallmentScheduleMapper` |
| 등록·수정·비활성화 | `CatalogService.saveInstallment()`, `deactivateInstallment()` |
| 카드 결제 예정 합산·실제 출금 | `PlanService.generate()`, `payCard()`, `confirm()` |
| 회차별 이력 | `installment_schedule`: 할부, 결제일, 금액, 상태, 연결 예정, 실제 납부일 |
| 등록·조회·결제 화면 | `common/card-editor.js` |
| 공통 예정 확정 모달 | `common/occurrence-editor.js` |
| 반복 목록·달력 | `pages/planned.js` |

`GET /api/installment-schedules`는 회차 목록을, `GET /api/occurrences/{id}`는 예정 한 건을 반환합니다. `POST /api/cards/{id}/payments`는 기존 `date`, `amount`에 선택적인 `billingMonth` (`YYYY-MM`)를 받습니다. 생략하면 출금일의 월을 사용하며, 이제 해당 결제 예정도 함께 완료합니다.

등록·납부는 Spring 트랜잭션과 기존 공통 PostgreSQL advisory lock을 사용합니다. 납부 이력에는 예정 ID가 연결되고, 회차 이력에도 같은 예정 ID가 기록됩니다.

## 검증

- `gradlew.bat test`: 월말·윤년·마지막 회차 차액 등 단위 테스트.
- `node tests/page-modules.cjs`: 11개 화면과 할부 표시·카드 상세의 예정 확정 연결.
- `InstallmentFlowIntegrationTest`: 실제 PostgreSQL에서 등록, 여러 할부 합산, 지연 납부, 완납, 중복·부족액 거부, 수정·비활성화, 결제일 변경, 마이그레이션 재실행 검증.

통합 테스트는 `application.yml`을 사용하지 않습니다. `127.0.0.1:55439/installment_test`의 별도 임시 PostgreSQL을 `installment_test` 사용자로 준비한 후 `ASSET_INSTALLMENT_DB_TEST=true`를 설정하고 `gradlew.bat test --rerun-tasks`로 실행합니다. 실제 개인 데이터 DB를 이 주소로 연결하지 마세요. 테스트가 전용 DB에 스키마와 검증 데이터를 생성합니다.
